# 01 产品定位与原则

- **定位**：整套产品的总纲。状态：已定稿。最近更新：2026-08-17。

## 一句话定义

一套融合了完整 AI 开发工程方法论的编程系统：从需求讨论到开发完成上线运营，让哪怕小白也能用较低人力投入，产出结构干净、前端不丑、可扩展、可上线的产品。**核心卖点是下限高。**

产品形态可以理解为：**一套带工程工作流、带对话自动管理的 Claude Code**。用户想省心就全托管，想掌控就随时进任意对话。

## 解决什么问题

现有编程 agent 工具（Cursor / Windsurf / Devin / Claude Code 等）产出方差极大：专家能出好东西，小白拿到的是烂摊子——

- 逻辑全部塞进两三个文件，完全不考虑可扩展性和模式设计；
- 前端默认不用组件库甚至手写组件，没有视觉方案，效果差且**积重难返**（烂在结构里，后期改不动、回不去）；
- 不管代码规范、不管项目管理，你说啥它做啥。

这些工具提供了灵活，但对 code 场景不够专精。我们把一整套 AI 开发方法论焊进系统，专治「下限低」和「积重难返」。

## 四大支柱

1. **项目管理可视化**
2. **多任务运行并行化**
3. **开发工程流程化**
4. **AI 开发规范化**：项目规范、编码规范、前端风格规范——前端尤其重要。

## 核心理念：约定优于提示词

类比 Rails 的 convention over configuration：一个跟着约定走的菜鸟，产出结构比中级选手自己撸的还干净；下限抬高，上限几乎没压。

落法：好结构不能靠用户会问（小白不知道该要求「按职责拆文件」「先建设计系统」），必须让 agent **自动遵守约定**，用户不需要懂、甚至不知道有这些约定。所以方法论必须活在**绕不过去的基础设施**里（scaffold / lint / gate / checkpoint），不能只活在 prompt 里——prompt 会被长上下文稀释，规则会漂。

## 抬下限的三招

1. **好路径必须是默认路径。** 拆模块、先设计后编码、先 token 后页面，都是引擎的出厂行为，不等用户想起来要求。
2. **坏模式直接拒绝。** 手写组件库、单文件堆一切、没 token 写业务页——命中就打回。
3. **专业经验焊进脚手架。** 初始化就生成 token + 组件库 + 模块骨架，小白直接站在有设计系统的项目里，继承而非学习。

关键原则：**预防优于矫正。** roadmap → 脚手架 → 代码这条线要真走，让代码从一开始就没机会烂。

## 三条护栏（防止方法论反噬）

1. **意见分两层颗粒度。** 通用层（拆文件、先 token 后页面、用组件库、单一数据源）硬执行；项目层（框架、状态库、视觉风格）初始化时让用户/agent 选，选完再硬执行。
2. **流程要快、要隐形。** agent 替用户填表（草拟 roadmap、提一版 token、搭骨架），用户只审批和改。方法论在台面下跑，用户掌舵，不当抄写员。
3. **抬下限不压上限。** 每条硬规则留逃生舱，长成中级的用户能突破，不会因工具太轴而毕业离开。

## 生命周期范围与策略

目标覆盖七阶段：需求讨论 → 产品调研 → 需求落档 → 项目管理 → 产品开发 → 产品上线 → 产品运营。

策略：核心是同一个「约束 + 生成」方法论引擎（拆分规则、lint、脚手架、checkpoint），阶段是它的应用面。先在 dev + 前端两个下限最低、痛感最强的环节验证引擎，再铺其他阶段。

前端质量标准（用户原话）：「你让 AI 随便写一个简单的网页，他都没法做到写出 AI 味浓以及很难看的情况」。解法：约束活在项目脚手架里，初始化生成一次，之后随手写页面也自动继承。

## 多模型

支持 Anthropic Messages、OpenAI Chat / Responses、DeepSeek 及任意 OpenAI 兼容端点。定位：**地基，不是招牌**——为了成本、可用性、可替换性。在本项目里它还有一层产品含义：**AI 创建对话时自己选模型**（见 [02](02-对话-子agent与模型选择.md)），成本控制是设计目标。

## 命名

**keel = 龙骨**：船能扛风浪全靠龙骨——藏在船底看不见，但整条船的稳定与航向都由它定住。与「方法论活在基础设施里、看不见但抬下限」严丝合缝。npm 发布名 `keel-code`，命令 `keel`。

## 差异化一句话

市面工具卖「灵活」，我们卖「确定的下限」：柔性的对话使用方式（可以退化成普通 Claude Code）+ 刚性的开发质量流程（设计先行、绑定 review 闭环、强制层拦违规）。
