# 02 对话、子 agent 与模型选择

- **定位**：多对话的组织方式、三层执行单元、名册数据结构、上下文路由规则、创建对话时的模型选择。状态：核心规则已定（2026-08-17 按用户澄清重写）。最近更新：2026-08-17。

## 三层执行单元（先把概念钉死）

| 层 | 是什么 | 用户能否进入 | 生命周期 | 典型用途 |
|---|---|---|---|---|
| **对话（Conversation）** | 一条持久会话。项目里第一条是**主对话**；主对话可以**启动其他对话**，用户在 UI 里也能直接新建 | **能**，任意对话随时进去聊 | 长期，按上下文领域存在（整个前端、某引擎、Infra、某业务模块、需求讨论、杂活…） | 长期养着的前端对话、模块开发对话、需求讨论对话 |
| **子 agent（Subagent）** | 对话内部的一次性委派：`clean`（干净上下文只带任务）或 `fork`（复制父对话已有上下文前缀 + 任务），干完把结果交回发起它的对话 | 默认不进入；轨迹在 UI 里挂在父对话下可查看 | 一次任务 | 独立 reviewer、并行探索、跑测试回归、按摘要重建认知 |
| **workflow 编排** | 脚本化地组合多个子 agent（并行 / 流水线 / 循环直到干净），控制流由代码决定 | 否 | 一次运行 | 多维度 review、批量迁移、多方案评审（M5） |

不要混淆：**对话不是子 agent**。主对话「启动一个前端对话」得到的是一条和它平级的、用户能进去的会话，不是一个用完就散的工人。

## 总则

- 用户始终可以和**任意**对话直接沟通。
- 主对话相当于托管入口：对全局交付负责，**独占对话的创建、选择、复用、调度、归档权**（用户手动在 UI 新建除外，新建后同样进名册）。
- 对话**没有固定编制**：我们规定的只是流程。「要做 xxx 模块，就创建一个 xxx 开发对话」；用户显式说「建个杂活对话」也照建。
- 提示词结构：**只有主对话的系统提示词多一段调度职责**；其他所有对话共用同一套 base 提示词（方法论），创建时额外注入一段职责。
- 柔性边界：对话边界服务于**上下文质量**，不用于限制用户行为。用户拒绝推荐、坚持在当前对话继续，就继续执行——体验自然退化成普通 Claude Code + 多了个 review 工作流，可接受。

## 两类粒度（最锋利的一刀）

- **对话粒度 = 上下文领域**：一条对话对应一个长期稳定、内部高度相关的上下文领域。
- **交付粒度 = 可验收结果**：一次可验收成果（一条完整业务流程、一个可操作页面、一组能确认业务结果的接口）只是这条对话的一个**交付批次**。

推论：前端对话长期负责整个前端，内部连续完成多个交付批次，无需每批新建。项目变大后（后台管理端、营销站、可视化编辑器形成独立设计和代码边界）才拆新对话。

## 主对话拥有的工具

| 工具 | 作用 |
|---|---|
| `keel_providers_probe` | 探测本机已配置的 API 端点：连通性、时延、可用模型列表（附上下文长度、已知单价、能力标签、推荐档位） |
| `keel_conversation_create` | 创建对话：标题、职责段、**模型（provider + id + 推理档）**、代码范围、初始消息 |
| `keel_conversation_list` | 名册视图：所有对话的导航信息 + 新鲜度标记（不加载任何对话内容） |
| `keel_conversation_send` | 给某条对话追加一轮消息（活的直接入队，睡着的冷唤醒） |
| `keel_conversation_read` | 读某条对话的摘要 / 最近结论（导航用，不是全文） |
| `keel_conversation_handoff` | 把当前用户意图连同必要上下文交接给另一条对话（推荐流程用） |
| `keel_conversation_archive` | 归档 |

非主对话只拿 `keel_conversation_list`（导航）和向主对话汇报的 `keel_conversation_send`（目标固定为主对话）。发现需要新对话时，回到主对话创建（UI 上给一键「让主对话创建」）。

## 创建对话时的模型选择（成本与效率）

流程固定为三步：**探测 → 挑选 → 启动**。

1. `keel_providers_probe` 返回每个端点的模型清单。数据来源：pi-ai 内置模型目录（含单价与上下文长度）+ 端点 `/models` 实时列表 + 本机 `~/.keel/settings.json` 里用户标注的档位。
2. 主对话按任务性质挑：需求讨论 / 设计 / 复杂实现用强模型；跑测试、批量改名、文档修剪、格式修复用便宜模型；reviewer 默认用与实现者不同的强模型（避免同一模型的盲区）。用户可在设置里**锁定**某类对话的模型，锁定优先于 AI 判断。
3. `keel_conversation_create` 带上 `model`。对话进行中用户可随时换模型（同 Claude Code `/model`），换模型的事件写进会话日志。

每条对话记录累计 token 与估算费用，名册和看板都能看到——成本可见是选模型这件事有意义的前提。

## 子 agent 工具

`keel_agent_run({ mode: "clean" | "fork", task, model?, tools?, outputSchema? })`

- `clean`：新上下文，只带 base 方法论 + 任务描述（+ 可选结构化输出 schema）。reviewer 就是这样跑的。
- `fork`：把父对话到当前为止的上下文前缀复制给子 agent，再加任务。适合「顺着我现在的思路并行试一个方案」。
- 结果作为工具返回值交回父对话；子 agent 的完整轨迹持久化，UI 里挂在父对话下面。
- 子 agent 里再开子 agent：v1 不允许（避免失控），后续按需放开一层。

## 名册（Registry）

主对话拥有「项目团队通讯录」：知道有哪些对话、各自掌握什么上下文、做到哪、是否适合继续接活。

### 摘要 schema（每条对话一条记录）

| 字段 | 含义 |
|---|---|
| id / name | 唯一标识 / 显示名 |
| kind | main / conversation |
| role | 一句话职责 |
| context-scope | 上下文领域 |
| code-range | 负责的代码范围（glob，同时是边界锚点） |
| model | 当前模型（provider + id + 推理档） |
| status | 空闲 / 忙碌 / 阻塞 / 已归档 |
| last-active-at | 上次活动时间（缓存判据） |
| base-commit | 上次确认的 commit |
| code-hash | code-range 当时内容的指纹，用于判过期 |
| current-understanding | 当前认知 |
| key-artifacts | 关键产物位置 |
| recent-work | 最近一批做了什么 |
| unresolved | 未解决事项 |
| suitable-for / not-suitable-for | 适合 / 不适合接什么 |
| cost | 累计 token / 估算费用 |
| summary-version | 摘要更新时间 |

正文另写一段自然语言简述，给主对话路由用。

### 新鲜度规则：摘要导航，产物确认事实

- 摘要**只用于导航**；需求文档、设计文档、任务状态、review 记录、代码仓库才是**长期真相源**。
- 对话被唤醒时，先拿摘要去定位相关文档和代码，核对当前 commit，再干活。
- 被读时用当前状态对一下 code-range 有没有被动过，被动过就标 **stale**，强制先重建认知再干活。

### 复用还是新建：判据序

1. **缓存是否还在**：`last-active-at` 距今是否在该 provider 的提示缓存 TTL 内（Anthropic 5 分钟 / 可选 1 小时；DeepSeek 自动缓存按其规则）。在 → 继续复用。
2. 标题是否匹配 → 匹配则继续。
3. 摘要是否匹配 → 匹配则继续。
4. 代码 / 模块范围是否匹配 → 都不匹配 → 新建。

缓存经济学（用户原话）：缓存丢了之后复活旧会话的重建成本很高，不如新建一个，让 AI 自由探索精准上下文——成本一样甚至更低，且上下文更准。缓存失效后，旧对话主要作为**知识来源**：按其摘要创建新对话（可用 `clean` 子 agent 先重建认知），避免背着大量低价值历史上下文工作。

### 名册数据的家

会话事件为主（每条对话的会话日志里追加 keel 名册事件，可回放、冷唤醒后还在）+ 仓库投影为辅（`.keel/agents/*.md`，人能看、git 有版本、换机器不丢）。

## 生命周期（推荐默认，按需临时创建任何对话都合法）

| 类型 | 生命周期 |
|---|---|
| 主对话 | 贯穿整个项目，全局视图 + 调度权 |
| 产品 / 需求对话 | 项目长期存在 |
| 前端对话 | 长期存在，持续积累视觉与组件上下文 |
| 模块开发对话 | 模块长期存在，超出模块边界时新建 |
| Infra 对话 | 基础设施阶段存在，后续按需唤醒 |
| reviewer | clean 子 agent，按批次一次性，干净上下文 |
| 修复 | 默认由原实现对话继续（代码是它写的） |
| Bug 对话 | 按问题创建，必要时读模块对话摘要 |

## 交互模型细则

- **推荐可以拒绝**：任何对话发现用户意图进入新领域，就推荐起个新对话；用户拒绝就在原地做。
- **创建权回收**：非主对话发现需要新对话时，回到主对话创建（UI 一键）。
- **同步义务**：用户直接在某条对话里改了需求 / 进度，新决定和摘要必须同步回名册和相关文档。
- **验收失败**：由原实现对话继续改。
- **同模块默认串行**：支持 fork 子 agent 并行作为高级能力，明确不提倡；需要文件隔离时走 worktree（[M10](../roadmap.md#m10)，[09](09-并行与安全网.md)），系统不自动把副本合回主仓。

## 文档修剪对话

项目的文档管理员：收集各对话产生的新决定；判断哪些进需求 / 设计 / roadmap / 决策记录；删过期、重复、被推翻的内容；维护文档间一致性；通知主对话和受影响对话。提交后兜底运行。边界：只整理、去重、同步、标记过期；**不创造产品决定**；不无痕删除历史决策；发现冲突交主对话。

## 全局记忆

对齐 Claude Code / Codex 现有机制。共享边界：开发偏好、通用规范、常用技术、用户习惯可跨项目共享；需求、代码事实、密钥、项目决策只属于当前项目。

落地见 [08](08-日常驾驶.md)：用户级 `~/.keel/MEMORY.md` + 项目根 `AGENTS.md` / `CLAUDE.md`。说明书是参考，和规范、闸冲突时规范和闸说了算。不自动读 `~/.claude` / `~/.codex`。
