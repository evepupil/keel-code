# 05 底座选型与调研

- **定位**：2026-08-17 的底座调研与决策记录：为什么离开 DeepSeek Harness（dsh），候选方案对比，最终选择「自研工具本体 + pi 内核」，风险与退路。状态：已决。最近更新：2026-08-17。

## 结论

**自研 keel-code 工具本体**（自己的 CLI + 本地服务 + Web 工作台 + 对话管理），**引擎层不从零写**：嵌入 pi（Earendil，`@earendil-works/pi-ai` / `pi-agent-core` / `pi-coding-agent`，MIT）作为发动机；方法论 / 闭环 / 名册 / 界面全部放在自己的层里；引擎调用收敛在 `@keel-code/engine` 一个包内，保留换引擎的可能。

## 为什么离开 dsh

- 时间线：2026-08-13 开源，npm `0.1.0-rc.6`，官方标注 developer preview、明示会有破坏性变更（[GitHub](https://github.com/deepseek-ai/deepseek-harness)、[VentureBeat](https://venturebeat.com/technology/deepseek-harness-launches-as-open-source-rival-to-claude-code-alongside-v4-pro-on-api-with-higher-prices)）。
- 社区一手评测的共同结论：agent 循环没有成熟的「自我纠错」（不会自动跑类型检查 / dev server 验证再修）；Web 版默认关掉 Skills 且不报错、要手动 patch 配置、端口手管；短期内 Claude Code 仍是最优解（[掘金实测](https://juejin.cn/post/7673810995882672128)、[CSDN 三方对比](https://blog.csdn.net/aidoudoulong/article/details/163759887)、[知乎讨论](https://www.zhihu.com/question/2071331484284220938)）。
- 部署摩擦：1GB 内存跑不起、ARM 要手动编译 node-pty、approve-scripts 要人工介入（[80aj](https://www.80aj.com/2026/08/15/deepseek-harness-deployment-issues/)）。
- 我们自己在旧线 spike 中的体感一致：启动 27 秒、插件路径必须 `file://`、客户端包要 junction 挂载、手写免构建 bundle、一个坏工具毒死全部会话、孤儿进程丢 stderr。
- 值得借鉴的设计思想（已吸收进本项目）：会话 = 只追加事件日志、可进入的持久子会话、单调 guard、聊天里的自定义节点、把 Claude Code / Codex 当执行器。

旁证：Anthropic 2026-03《Harness Design for Long-Running Application Development》——规划 / 生成 / 评估三 agent + 上下文重置 + 结构化交接产物 + 独立评估者（[InfoQ](https://www.infoq.com/news/2026/04/anthropic-three-agent-harness-ai/)、[Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)），与本项目「独立 reviewer 干净上下文 + 文档是真相源」同向。

## 关键设计决策（相对 dsh 时期）

1. 对话 / 子 agent / workflow 三层都是 keel 层概念，不依赖引擎的子 agent 功能；每条对话 = 一条独立引擎会话。
2. reviewer = clean 子 agent + 强制调用带 schema 的 `submit_review` 工具，结论在代码里分类路由。
3. 强制层走 `tool_call` 拦截，只对实现阶段的对话生效，逃生舱留痕。
4. 权限审批自己做：ask / 白名单 / 全放三档（M5），沙箱后置。
5. 设计确认：Web 内可编辑视图 + 划选批注，agent 读 git diff 回显理解，冻结写标记并提交；全程文件为准。
6. 创建对话时探测端点选模型（见 [02](02-对话-子agent与模型选择.md)）。
7. Windows 一等公民：Node 22+、不用 Bun、v1 不引入 node-pty 等原生模块。

## 风险与退路

- pi 是 0.x、每周发版：锁版本 + 全部调用收敛在 `engine` 包 + MIT 允许必要时 vendor。
- pi 缺权限 / MCP / 子 agent：按 keel 的方式实现，工作量计入 M2 / M5。pi 刻意把搜索 / 浏览器 / LSP / rewind 留给扩展；M8 受控打开加载器（隔离 `~/.keel/pi`，不继承 `~/.pi/agent`），见 [07](07-能力插槽与扩展.md)。
- 若 pi 内核在 M1 实测暴露硬伤：`Engine` 接口不变，切到 OpenCode 服务端。
- dsh 6–12 个月后再评估，届时可做一个 dsh 适配。

## 已拍板事项（2026-08-17）

- 仓库新起（不克隆旧线），旧线 `evepupil/keel-code` 归档留作参考。
- 技术栈：Node 22+、pnpm、TypeScript strict、Biome、vitest；服务端 Hono + ws；Web React + Vite + Tailwind（shadcn/ui 作基础组件）+ CodeMirror 6。
- Web 优先，TUI 后置（M6 复用 pi 终端界面）。
- v1 不做 Claude Code / Codex 执行器，只留接口。
