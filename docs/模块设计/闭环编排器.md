# 闭环编排器

- **模块定位**：keel 的核心 IP——把「实现 → review → 确定性修复 → 验收」从提示词约束升级为机械执法。批次上报工具是绑定入口，独立 reviewer 是 clean 子 agent，分类路由在代码里，review-pass 记录用工作树指纹，提交门禁凭记录放行。
- **对应代码**：`packages/loop/`（门禁判定在 `packages/guards/`）
- **所属里程碑**：[M3 — 闭环编排 + 强制层](../roadmap.md#m3)（能力挂钩在 [M8](../roadmap.md#m8)）
- **当前状态**：进行中（M3 主体已落地：上报工具 / 独立 reviewer / 分类路由 / 修复循环 / review-pass / 待决策 / 提交后 credit 刷新 / review 卡片）
- **最近更新**：2026-08-17
- **设计依据**：[设计/03](../设计/03-开发闭环与检查点.md)

## 职责与边界

接收实现对话的批次上报（`keel_batch_report`），派 clean 子 agent 复核（强制调用 `submit_review` 工具给结构化结论），分类路由：确定性工程问题 → 修复指令作为工具返回值回传（≤3 轮）；产品 / 需求问题 → 追加 `docs/review/待决策.md` 并要求转述用户、批次挂起；通过 → 写 review-pass（树指纹）→ 输出验收简述模板；连续 3 轮不过 → 升级为待决策。

不做：UI（Web 渲染 keel 条目）、验收动作本身（用户行为）。

## 结构与数据流

```
实现对话 ──调用──▶ keel_batch_report(batch, scope?, designDoc?)
                       │ roster.runSubagent({mode:'clean', task: reviewerPrompt, outputSchema: REVIEW_SCHEMA, model: 反相位})
                       ▼
                 独立 reviewer（干净上下文）── submit_review ──▶ {verdict, summary, findings[{issue, category, file, suggestion}]}
                       │
                 分类路由（代码）
                 ├─ deterministic → 返回修复指令 → 实现对话修复 → 再上报（≤3 轮）
                 ├─ decision      → 追加 docs/review/待决策.md → 要求转述用户、批次挂起
                 ├─ pass          → 写 review-pass（treeHash）→ 允许提交、输出验收简述
                 └─ 3 轮不过      → 升级为待决策
git commit ── tool_call ──▶ commit-gate（guards）：review-pass 存在且 treeHash 一致，且项目门禁通过
提交成功 ── tool_result ──▶ 刷新 review-pass 的 treeHash

packages/loop/src/
  report/        keel_batch_report 工具定义与执行
  reviewer/      reviewer 提示词、REVIEW_SCHEMA、submit_review 工具
  route/         分类路由（纯函数）
  credit/        review-state 读写、treeHash 计算
  decisions/     待决策文件读写
  acceptance/    验收简述模板 + 验收卡条目
```

treeHash = `git status --porcelain`（剔除 .keel）排序 + `git diff HEAD`（剔除 .keel）的 sha256 前 16 位。

## 关键决策

1. **绑定入口是工具而非提示词**：不调用就没有 review-pass，提交被门禁拒——跳过闭环在机械上不可达（逃生舱 `commitGate:false` 留痕）。
2. **reviewer 每轮全新 clean 子 agent**：干净上下文 + 修复不能自证通过。
3. **结构化结论**：强制调用 `submit_review`（schema），分类路由在代码里，「分不清默认归待决策」是路由逻辑。
4. **修复回路走工具返回值**：模型同一轮内看到并继续修。
5. **review credit 用工作树指纹**；提交后刷新。

## 当前实现

`packages/loop/src/`：
- `report/orchestrator.ts`：`registerBatchReportTool()`——`keel_batch_report(batch, scope?, designDoc?)`（作用域 main + conversation）：读 review 状态定轮次 → `pickReviewerModel`（用户锁定 > 与实现者不同的 strong > 任意不同 > 同款）→ `SubagentRunner.run({ mode: "clean", tools: 只读集, outputSchema: REVIEW_SCHEMA })` → `classify` 路由 → 写状态 / 追加待决策 / 返回指令；每步 `parent.appendEntry("keel/review", …)` 供 UI 渲染；同时挂 `tool_result` 钩子在 `git commit` 成功后刷新 review-pass 的树指纹。逃生舱：`options.enabled()`（读 `.keel/config.json` 的 `loop`）。
- `reviewer/prompt.ts`：`REVIEW_SCHEMA`（verdict / summary / findings[issue, category, file, suggestion]）+ `reviewerPrompt()`（只读、复核清单、判定纪律、复验时带上一轮问题、必须调 `submit_result`）。
- `reviewer/model.ts`：`pickReviewerModel()`。
- `route/classify.ts`：`classify(verdict, round, maxRounds)` 纯函数 → pass / fix / suspend / escalate；`isNoopFinding` 过滤「无需修改」类条目；`formatFindings`。
- `credit/state.ts`：review 状态（`roundsSincePass` + `lastPass{tree, at, batch, sessionId}`）放 `~/.keel/sessions/<项目>/review-state.json`（不进仓库，避免工作副本漂移）；`credit/tree-hash.ts`：`git status --porcelain` + `git diff HEAD`（剔除 .keel）的 sha256 前 16 位；`credit/commit-detect.ts`：`git [全局选项] commit` 识别（guards 复用）。
- `decisions/file.ts`：`docs/review/待决策.md` 追加、列出（行号 + 所属批次）、解决（删行并清理空小节）。
- `acceptance/brief.ts`：验收简述四项模板。
- `prune/job.ts`：文档修剪 job——`git commit` 成功后（修剪自己的提交除外）异步派 clean 子 agent，按 `git show --stat` 检查对应模块文档 / roadmap / 双向链接，只整理不决策，纯文档提交，结果写 `keel/doc-prune` 条目；`.keel/config.json` 的 `docPrune` 可关。

服务端：`services/loop.ts` 装配（与 guards 一起），`GET /sessions/:id` 返回 keel/* 条目；Web：`ReviewCard`（动作徽标 / 轮次 / reviewer 模型 / 费用 / findings 分类 / 树指纹 / 查看 reviewer 轨迹），消息与条目按时间合并成时间线。

## 验证方式

- 纯函数单测：`route/classify.test.ts`（pass / noop-pass / fix / escalate / suspend / 混合）。
- 端到端 `loop.test.ts`（mock 模型，真 git 仓库）：无 review 的 `git commit` 被门禁拒 → 写文件 → 上报 → reviewer 第 1 轮 fail（硬编码）→ 修复 → 上报 → 第 2 轮 pass（含验收简述模板）→ `git commit` 放行、日志有提交 → 提交后 credit 树指纹刷新 → `keel/review` 条目 [fix, pass]、reviewer 用了反相位模型 `mock-strong`、两个 reviewer 子会话挂在实现对话下；只有 decision 的结论 → 挂起 + `docs/review/待决策.md` 落档 + 条目 suspend。
